# Proposed VFS maintenance handoff

Status: **candidate design and evidence packet**, not an operational procedure. The pure transaction planner and bounded loop are being implemented; host adapter, startup barrier and end-to-end evidence remain required. Tracked by [#50](https://github.com/xtreemze/slipmat-companion/issues/50) and [#139](https://github.com/xtreemze/slipmat-companion/issues/139). This proposal does not authorize deleting either media copy, recreating a Jellyfin library, or bypassing the public unmount guard.

The transaction loop operates only on the maintenance intent embedded in the existing migration job. Its adapter must hold the authoritative journal and host exclusion leases for the entire run, compare the complete job snapshot revision for each durable update, and independently revalidate all custody and exact mount identity at each effect. A planner observation is not a lease or an OS-level proof. The adapter must classify a mountpoint without a mount as such only when it is owned and verified empty. Newly created mount identity must be verified and durably journaled before proceeding; if a crash intervenes, recovery blocks rather than adopting a mount by path or remote name. Stop/recovery remains blocked until a verified host adapter and startup barrier exist.

Live-main refresh: Companion `01eba6c9dcdd598e308fed1a7fd440925dfe4827` (release 0.5.2.12) targets Jellyfin 12.4.0. Its migration and mount handoff behavior described below is unchanged by #153. There were no open Companion PRs when checked. The operator reports a separate full read-only hash comparison in progress; its result is pending and it is not the migration job's full two-way downloaded-content verification.

## Why a handoff is required

The existing local-to-VFS cutover checks `IsScanRunning`, then renames the local directory and mounts at the same path. A scan may start after that check. The rollback worker disables the profile and calls the public unmount action, which correctly rejects an attached library. Replaying `RollingBack` after a crash can also encounter a backup already moved back to the original path and report `rollback-backup-missing`. None of these paths has been certified on the production host.

Jellyfin 12.4's [`Folder.ValidateChildrenInternal2`](https://github.com/jellyfin/jellyfin/blob/v12.4/MediaBrowser.Controller/Entities/Folder.cs) skips a top-level folder when it is inaccessible or empty and finishes enumeration before mutating its children. [`DirectoryService.IsAccessible`](https://github.com/jellyfin/jellyfin/blob/v12.4/MediaBrowser.Controller/Providers/DirectoryService.cs) tests whether the path has entries. These are useful failure protections, not an exclusion transaction: a scan can cross a swap boundary after its accessibility check, retain an earlier listing, or encounter changing descendants. The same code can remove catalog entries absent from a successful enumeration. Do not assume all missing-path cases preserve identity.

Jellyfin's [12.4 `ILibraryManager`](https://github.com/jellyfin/jellyfin/blob/v12.4/MediaBrowser.Controller/Library/ILibraryManager.cs) exposes scan observation and scheduling but no exclusive scan/reader lease. Removing and re-adding a media path is not this transaction: the [12.4 implementation](https://github.com/jellyfin/jellyfin/blob/v12.4/Emby.Server.Implementations/Library/LibraryManager.cs) changes the library path configuration, and adding a shortcut also removes content-type overrides. Keep the original virtual folder and its path attached throughout.

## Minimum capability and choices

**Offline maintenance is the initial candidate.** A host-controlled maintenance runner, separate from the stopped Jellyfin process, must exclusively own the exact library path, mount namespace, migration journal, profile configuration and mount lifecycle. It must prevent Jellyfin, Companion startup/reconcile, scheduled scans, other writers and media readers from accessing the path until recovery has reached a verified stable state. It must be able to inspect the actual host and eventual Jellyfin mount namespaces and prove that its mount changes are visible to the restarted service. An operator or service supervisor must stop and keep the server stopped and prevent automatic restart until the runner explicitly releases it. A Companion background worker cannot do this while its own host is stopped. The runner, its authenticated invocation, service supervision and on-disk compatibility are **not implemented**.

**Online alternative:** a supported Jellyfin host extension would need an exclusive, crash-recoverable lease that blocks new scans and monitor work, drains existing scans and path readers, prevents library/profile changes and guarantees that no path-dependent work resumes until the path is stable. The extension must expose a durable recovery barrier before ordinary server startup/scan processing and coordinate the managed mount in the same namespace. A point-in-time `IsScanRunning` check or `LibraryMonitor.Stop()` alone is not such a lease. Whether Jellyfin can provide this with a modest upstream change is unknown; its public 12.4 interface does not establish that capability. This alternative preserves availability but has a substantially wider host integration and proof burden than offline maintenance.

For either choice, the operator needs a tested method to keep the host quiescent across crashes and reboot, service-account access to the local tree, and a managed rclone mount whose ownership can be proved. If the environment cannot provide these, stop without swapping. No manual sequence in this document is a substitute for an implemented, tested transaction.

The smallest executable route is therefore not available in the current release: finish the same-job recovery and its existing verification gate; deploy a reviewed Companion-owned offline transaction adapter and supervised runner; then execute that adapter under proven systemd quiescence. The runner must call the same versioned migration authority rather than directly patching its journal or introducing a second independent migration state machine. A manual directory rename and mount cannot complete the existing worker's journal, reconcile its profile or provide its crash recovery. Nor can the online worker continue after Jellyfin stops, because it is hosted by Jellyfin. This is a cross-domain service/runner contract, not a routine unmount sequencing edit.

The minimum implementation boundaries are: (1) the existing migration coordinator admits a specific verified job to offline maintenance and records immutable custody and expected transition; (2) a narrow shared transaction engine, invoked by an authenticated service-supervised runner while Jellyfin is stopped, owns the same durable job and serializes profile/mount access; (3) mount lifecycle exposes internal instance-bound operations only to that transaction, leaving the public attached-library guard unchanged; (4) startup reconciles any unfinished transaction before library scans or reconciler activity and refuses normal startup on ambiguity; and (5) the coordinator reads back the durable stable result before promotion. Exact process ownership, privilege separation and startup barrier require a concrete host design and review. `CloudMigrationStore.SaveAsync` currently writes a temporary file then renames it, but does not establish the proposed flush/directory-sync durability guarantee; that guarantee must be implemented and tested rather than assumed.

## Proposed custody and journal contract

One existing migration job remains authoritative. Before any side effect, persist and durably flush a versioned intent containing: job and direction; exact normalized original, backup and mount paths; library identity and single-location binding; profile ID, enabled state, remote and path; prior scan policy; source manifest and successful full two-way downloaded-content verification; expected local filesystem identity and backup identity; and a transaction ID. Reject competing jobs, changed bindings, unexpected files, symlinks, foreign mounts or a stale intent. Never store credentials. Recheck these facts immediately before each irreversible-in-place transition.

For a mounted source, capture the Linux mount namespace and exact mount instance from `/proc/*/mountinfo` (including mount ID, device, mount point, filesystem type and expected remote/source), then revalidate at the unmount boundary. Existing `CloudMountObservation` reports ownership/readiness but does not expose instance identity. A matching remote string or marker is not proof that the mount is the same instance. An unmount operation must fail closed on replacement, ambiguity, a foreign mount, inability to prove namespace visibility, or busy/open handles; it must not force or lazy-unmount. Keep the generic user unmount guard unchanged. A job-scoped internal operation is permissible only under the maintenance lease and the exact custody and mount checks above; it is not a general attached-library bypass.

Record durable intent **before** each side effect and durable observed completion **after** it. At minimum distinguish: `prepared`, `source-move-intent`, `local-backup-observed`, `mount-intent`, `vfs-mounted-observed`, `rollback-unmount-intent`, `vfs-unmounted-observed`, `local-restore-intent`, `local-restored-observed`, `profile-policy-restored`, and `stable`. These are proposed transaction substates, not current API values. Journal writes need atomic replacement and crash durability, including parent-directory synchronization where supported; persistence semantics must be tested on the target filesystem. A replay classifies the live paths, mount instance and journal together. It must never infer success from a missing backup alone, overwrite a path, delete nonempty directories, or proceed through an ambiguous state. Retain both remote media and the local tree throughout.

## Proposed offline sequence

1. While the local library is still serving, finish additive copy, full two-way downloaded-content verification and source/binding checks. Record library ID, path, representative item IDs and playback baseline. A subset diagnostic is not this verification.
2. Enter a supervised maintenance window. Stop and hold Jellyfin and all other path readers/writers; establish exclusive ownership, verify no scan or process can resume, and record the service and mount namespaces. Recheck no profile or filesystem custody change occurred. Run the final incremental copy and full verification while the source is stable. If any prerequisite fails, leave the original tree authoritative and do not swap.
3. Journal intent, rename the local tree to a collision-free sibling backup on the same filesystem, and durably record the observed identity. At the original library path create only the empty mountpoint required for the managed VFS. Mount and verify the exact instance, remote and bounded service-account reads in the eventual Jellyfin namespace. Preserve the existing virtual folder/path; retain the backup. On failure, under the same exclusive maintenance lease recover the local tree or remain stopped with an explicit recovery-required state.
4. With the VFS stable, release the maintenance barrier and start Jellyfin. Read back the installed plugin and server versions, exact library ID/path and representative catalog IDs; validate bounded service-account reads and representative playback. A scan and post-scan identity comparison are separate evidence. Keep the local backup and rollback capability. No finalize operation is authorized here.
5. For rollback, re-enter the same maintenance barrier. Verify the same job, backup identity, library/profile bindings and exact managed mount instance. Journal unmount intent; unmount without force; independently verify the exact mount is gone and no replacement is present. Remove only a verified empty mountpoint, journal restore intent, rename the retained local tree back to the original path, and verify its identity and readable content. Restore the prior profile and scan policy, journal a stable local state, then restart Jellyfin and verify library identity, catalog and playback. Retain all cloud objects.

The target host must explicitly establish what can be durably synchronized, how it prevents automatic service restart, and whether a stopped process's mount namespace survives and is shared with the runner. If any of these cannot be demonstrated, a host-specific implementation is required; this packet does not assert that the proposed sequence works there.

## Read-only systemd host preflight

The reported host uses a Linux system service. The service unit name, service account, mount namespace, source state and supervisor behavior remain **unverified**. SSH access is a transport only; it does not establish authority to stop services or mutate media. Run the following only after authenticating as the correct account, substituting values obtained from the host. These commands are observational and must not be combined with service restart, mount, unmount, journal editing or media changes. Avoid printing credentials, environment files, API keys or rclone configuration. If permission denies a read, record the denial; do not infer the result.

1. Identify the actual Jellyfin unit and inspect only non-secret properties. Inspect matching timers, dependencies and any container/supervisor separately; `Restart=` alone does not exclude other automatic starters.

   ```sh
   systemctl list-units --all --type=service 'jellyfin*'
   systemctl show UNIT --property=Id,LoadState,ActiveState,SubState,MainPID,User,Group,Restart,RestartSec,FragmentPath,DropInPaths,Requires,Wants,PartOf,TriggeredBy
   systemctl list-timers --all
   ```

   Review the unit and any identified overrides for non-secret restart, namespace and dependency settings without copying `Environment=`, `EnvironmentFile=` or command-line secrets into the evidence. Establish which administrator or supervisor can hold the service stopped across crashes and reboots; observation does not establish that this control is available or authorized.

2. With the unit's nonzero `MainPID`, compare the service's mount namespace with the prospective runner and inspect the exact source and prospective mount path. Use the path supplied by the journal, not a guessed mountpoint. `findmnt` output can contain provider-specific source names; redact sensitive components before sharing. A namespace match at one instant does not prove it survives a service restart.

   ```sh
   readlink /proc/PID/ns/mnt
   readlink /proc/self/ns/mnt
   findmnt --target /mnt/T7/Music --output TARGET,SOURCE,FSTYPE,OPTIONS
   cat /proc/PID/mountinfo
   ```

   Filter the mountinfo locally to the exact escaped mountpoint and its covering/stacked entries; avoid copying unrelated paths. Capture mount ID, parent ID, device, root, mountpoint, filesystem and source. Compare against the configured profile and the runner's view. If the process is containerized or inaccessible, identify the host-to-service namespace mapping before designing a runner. Mount-table metadata is not proof that directory reads or media playback succeed.

3. Read the existing migration job through the authenticated administrative API or dashboard, recording its ID, phase/code, source, backup path if present, profile/remote binding, verification and baseline history without tokens or private provider details. Compare those fields to the saved disabled profile and the existing single-path Jellyfin Music virtual folder. Read-only filesystem metadata can then establish whether the expected paths exist and whether they are directories on the same filesystem:

   ```sh
   stat -c 'path=%n device=%d inode=%i mode=%A owner=%U:%G' -- /mnt/T7/Music
   stat -c 'path=%n device=%d inode=%i mode=%A owner=%U:%G' -- BACKUP_PATH
   ```

   Inspect `BACKUP_PATH` only if the actual journal supplies it. A missing backup before cutover is expected; do not create or search by guessing a name. Inspect the parent filesystem and mountpoint metadata separately. Do not recursively enumerate a live remote or calculate a new baseline during this preflight. Do not treat inode, counts or a directory listing as content equivalence.

4. Through the existing authenticated Jellyfin and Companion administrative interfaces, read server and active plugin versions, migration status and the Music virtual-folder ID/name/locations. Record a small set of existing catalog item IDs and their paths and a normal playback baseline when the operator can do so without interruption. Redact access tokens and private paths as appropriate. These observations do not prove VFS mount readiness, rollback, or post-cutover identity. A future candidate requires the same readback after its actual installation and swap.

The preflight must also establish the exact service account's access through a bounded, read-only test executed under that identity using the host's approved privilege mechanism. `stat` as the SSH user alone is insufficient. No automatic unmount or service stop follows from successful preflight. The service supervisor, journal durability and namespace lifecycle must be designed and tested against observed facts before implementation or production execution.

## Jellyfin 12.4 in-process restart and administrator response

Observed on the target host: `jellyfin.service` runs as `jellyfin:jellyfin`, `PrivateMounts=no`, no `RootDirectory`, `Restart=on-failure`, `TimeoutStopUSec=15s`, and `SendSIGKILL=yes`. The source `/mnt/T7/Music` is on NTFS `fuseblk` `/dev/sdb1`; filesystem rename and durability behavior must be tested on the actual filesystem and mount implementation, not inferred from local ext4 tests. The UI restart initially logged shutdown notifications and `Preparing the database for shutdown...`, while the original PID remained. Subsequent issue #50 records successful startup and runtime .12 loading; the same PID was consistent with the in-process restart.

Jellyfin 12.4's [server entry point](https://github.com/jellyfin/jellyfin/blob/v12.4/Jellyfin.Server/Program.cs) performs UI-requested restart in a `StartServer` loop in the **same process**. Before host disposal and restarting the loop, it logs database preparation and awaits the provider's shutdown task with `CancellationToken.None`. For SQLite, the [provider](https://github.com/jellyfin/jellyfin/blob/v12.4/src/Jellyfin.Database/Jellyfin.Database.Providers.Sqlite/SqliteDatabaseProvider.cs) clears connection pools and requests `PRAGMA wal_checkpoint(TRUNCATE)`; a logged preparation line alone does not identify which operation is currently pending. A long checkpoint or an open reader is a hypothesis, not an observed cause. No PID change is required for a successful UI restart.

1. First observe, without another restart: check `systemctl show jellyfin.service` for `ActiveState`, `SubState`, `MainPID`, `Result` and stop timeout; inspect timestamped Jellyfin logs after the restart request for database checkpoint errors, disposal, a new startup sequence and `Startup complete`. Check API readiness and the active plugin version through the authenticated interface. Compare the runtime result to the on-disk DLL; matching a file hash alone does not prove the running assembly was reloaded. Retain the original migration journal and both media copies. Avoid displaying credentials or issuing SQLite write/checkpoint commands.
2. If startup completed and .12 is active, do not restart again. Continue with the original job's bounded diagnostic and record its result. If progress remains unclear, collect service status, subsequent logs, process wait state and read-only database file-holder evidence available to the administrator; a wait channel or an open file is evidence to investigate, not by itself a root cause. Preserve database, WAL and shared-memory files in place. A second restart request or a systemd stop while the first is unresolved may complicate diagnosis.
3. If a **separate** service-level restart becomes necessary, an administrator must first review the exact installed unit, drop-ins, `ExecStop`, `KillMode`, watchdog, other supervisors and systemd version. The current 15-second stop deadline plus forced final signal creates an avoidable shutdown risk. In a planned maintenance window, consider a temporary systemd runtime drop-in setting `TimeoutStopSec=infinity` and `SendSIGKILL=no`, then reload the manager and confirm both effective values with `systemctl show` **before** requesting a normal stop. The [systemd service documentation](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html) states that infinity disables the stop timeout; [systemd.kill](https://www.freedesktop.org/software/systemd/man/latest/systemd.kill.html) describes the final signal and warns that remaining processes can prevent restart when it is disabled. This is a proposed administrator procedure, not proof that the target unit has no other termination path; an existing active stop job or other supervisor may have its own deadline. Do not issue a stop until the administrator has verified those conditions and accepted the possibility of an indefinite wait.
4. After an ordinary stop request, wait for confirmed process exit and an inactive unit; do not use a forced signal, remove database/WAL files, or start a second server while the first remains. If shutdown does not finish, leave the unit and files intact and investigate with the administrator. Start only after clean exit, verify startup completion and active .12, then remove the temporary override through the administrator's normal configuration workflow and verify the intended service policy. Do not make changes to migration journals to get past restart.

The procedure does not authorize a storage cutover, unmount or local deletion. It is not an instruction to perform another restart while the present in-process restart is unresolved.

## Evidence required before production use

- Unit and filesystem integration tests for exact profile/library/job binding; mount-ID replacement and foreign mounts; marker-only or stale mount; busy unmount; nonempty mountpoint; path collisions; retained source/remote; and generic unmount still rejecting attached libraries.
- Crash/restart injection before and after every journal write, rename, mount, unmount and policy change, including already-restored local source. Assert exactly one stable authority or a stopped, actionable recovery state, and never overwrite or delete media.
- Real isolated Linux FUSE tests in the same namespace topology and service identity as production, including remount, lost daemon, permission denial, stalled reads, process death, host reboot and supervisor restart. Test that maintenance exclusion survives those faults.
- Real Jellyfin 12.4 integration on a disposable copy: concurrent scheduled/manual scan attempts and monitor events across every handoff boundary, item and virtual-folder IDs and relevant metadata before/after scan, open playback/read handles, failure recovery, and post-restart playback. Test a failed cutover as well as successful forward and reverse transitions.
- Exact candidate build and release checks, actual installed DLL/server version and ABI compatibility, source/remote whole-library verification, and production namespace/mount/readback evidence. Synthetic adapters and CI do not prove host behavior. Companion 0.5.2.12 targets Jellyfin 12.4.0; this does not certify the proposed unimplemented transaction.

Only after these gates may a specific host execution be considered. The maintenance window and cross-domain host contract require coordination with the operator; local deletion remains separately unauthorized.
