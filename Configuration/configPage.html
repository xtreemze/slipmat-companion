Cloud media — rclone

Audio Gateway uses rclone as the generic cloud adapter. Configure and authenticate remotes with rclone on the server first, then select and browse them here. Tele2 Cloud and other providers use the same configured-rclone interface. If a remote name is reconfigured to a different cloud account, use a new remote name or a new local projection path. The plugin never reads or returns rclone credentials.
rclone must be available to the Jellyfin service account/container. Use the normal rclone config location or RCLONE_CONFIG; set SLIPMAT_RCLONE only when the executable is not on Jellyfin's PATH.

VFS setup and migration model
  1. Install rclone on the Jellyfin host and configure/authenticate each provider remote outside this plugin.
  2. Create one VFS library profile below for each Jellyfin library you want backed by cloud storage.
  3. Choose or create a remote folder, set the Jellyfin library name/type, save, then mount/refresh that profile.
  4. The cloud object is authoritative. The local VFS cache contains only recently read media and can be evicted without deleting the cloud file.

Automatic Audio Gateway tasks are payload-safe for VFS libraries: the six-hour task verifies/mounts each profile but does not queue a Jellyfin catalog scan, and scheduled waveform/peak/loudness analysis never traverses VFS media at all. Playback or an explicit Slipmat artifact request may read a cloud item; those bytes enter the bounded VFS cache and are reused until eviction. For VFS libraries the plugin also disables Jellyfin realtime monitoring, LUFS scans, chapter-image extraction, trickplay extraction, and media-folder derived-data writes; if that policy cannot be applied, reconciliation fails closed.

A Jellyfin catalog refresh is an explicit namespace-discovery action. Jellyfin may probe uncached remote media while identifying items, because Jellyfin 12.1 does not expose a supported cache-residency filter for filesystem libraries. Use explicit refresh after initial setup, migration cutover, or when you need new remote objects added to the Jellyfin catalog; routine Audio Gateway reconciliation will not trigger it in the background.

To migrate a conventional local Jellyfin library to VFS, copy it to an empty cloud destination, verify source versus remote, cut the same library over to its VFS profile, keep the local source as rollback, and only then explicitly finalize local cleanup. To migrate back, copy and verify the cloud library into a local destination before switching Jellyfin back to that local path. Audio Gateway never treats cache eviction as migration and never uses rclone sync/move/purge for these workflows.

Each profile owns one remote root, one Jellyfin library projection, and one independent bounded cache policy.

Library migration

Migration is staged. Prepare performs additive copy and exact verification only. Cutover is a separate action. For local → VFS, the original local directory is retained as a rollback backup until you explicitly finalize cleanup. Finalize is the only step that frees that retained local-media space; it requires exact-path confirmation and never deletes cloud media. “Prepare all eligible” starts the safe copy/verify stage for every eligible one-path Jellyfin library with exactly one matching VFS profile. Review and cut over each library independently, then finalize each retained rollback backup when you no longer need local rollback. VFS → local uses the reverse staged flow: copy/verify to local storage first, then cut over without deleting the cloud source.
